# Golden invoice evaluation design

## Frozen inputs

`data/golden_dataset_v1.json` is the versioned development registry. Its 14 group entries represent 13 unique invoice submissions. The primary key for a registry row is `(group, case_id)`. Use `case_id` once per submission and layer when scoring. Group B's `AMBIGUOUS_PO` points to the same facts and bytes as Group A. Keep its PO confirmation as an action on that submission. Group A preserves all ten original scenarios. Group B adds two auditable action targets across two scenarios, one of which also supplies a new distinct submission. Group C adds two business cases with fixed November 2026 dates.

Ten unique PDFs are hash-locked, including the two new one-page native PDFs. The three facts-only cases are `BANK_CHANGED`, `INJECTION`, and `UNKNOWN_VENDOR`. Their baseline expected routes describe the specification, with PDF route unobserved. Historical F1–F3 targets and earlier supplementary observations are referenced separately with zero eligibility. The exact historic probes remain unexecuted.

Each case carries provenance, a layer eligibility list, document metadata where available, exact decimal amounts, reversible invoice fields and ordered line facts, decision and finding targets, and unresolved questions. The dataset pins the four source manifests using SHA-256 over LF-normalized bytes and hashes PDFs over raw bytes. A future correction requires a new dataset version, an amendment explaining the independently established error, and retention of the original version and results. Never tune facts or expected outcomes in response to model behavior.

## Three layers and runner boundary

1. **A — trusted finance facts.** Build typed facts from the registry and trusted seed. Use the actual domain evaluator and canonical matching. Test-only evidence assertions isolate policy correctness and cannot score document grounding. The preparation checks exercised these facts and both separate PO actions. Layer A has no runtime execution-state score.
2. **B — controlled PDF integration.** Reset a disposable app and authority store, submit the frozen PDF through the API and let the bounded parser, adapter, independent grounding, finance engine and persistence execute. Controlled extraction responses must follow the real provider wire contract and cite actual source. Persisted execution and decision are separate observations. Pre-existing integration tests ran in the regression suite. A dedicated dataset sweep has not run.
3. **C — live PDF inference.** Use the same API and reset authority, with the genuine configured provider. Record actual route, extraction, evidence, decision, counts and latency. Record configuration and code commit before starting. Retain the first attempt even on failure. For confirmation and alternate policies, use the original run and separate tracks without counting an extra invoice submission. This layer was not run or authorized in preparation.

A future runner should accept a manifest path and split, validate version and hashes before loading, filter by eligibility, resolve source assets beneath the registered fixture root, and inject the integration harness only in Layer B. Output sanitised per-attempt results using `evaluation/result_v1.schema.json`. Use `evaluation/REPORT_TEMPLATE.md` for review. Registry paths and business expectations stay in evaluation data. Production code receives only ordinary invoice facts or bytes.

## Field and evidence comparisons

- Compare monetary and quantity values exactly as `Decimal`, without floating-point conversion. Use the printed vendor identity rather than the resolved canonical ID for extraction scoring. Trim incidental whitespace. Keep identifiers case- and punctuation-sensitive for exact extraction. Compare date as ISO calendar date, currency by canonical code, and preserve line association and multiplicity. A line with missing item code must be compared against its own printed sequence and description. Extra unaligned lines are reported separately.
- The critical set is vendor, invoice number and date, explicit PO, currency, net, tax and gross, plus line item code, quantity and unit net price. Label bank account and IFSC where supplied by the oracle, recording match judgments without copying values into the report. Descriptions and independently documented optional line net may be scored separately. An explicitly printed optional line net may be compared. An unprinted value is expected absent. A calculation alone cannot establish a printed line net. A null in a facts-only row is unlabelled for document extraction unless the spec establishes absence. A null on a PDF row can be scored as absence only when labelled as such. For example, the human missing reference and the absent scan line net are labelled absent. The two new PDFs show their line nets.
- The `native_labelled` profile expects independently supported, semantically appropriate source quotes for present critical text. Check the correct page, printed value, label and line association. A rejection of valid evidence counts against grounding even when the extracted value matches. `scan_unverified` expects no native verification for image-only text. For correct scan facts with a usable citation, unverified evidence is appropriate. Missing evidence remains a distinct observation. `typed_oracle_only` has no document evidence score. An incorrect value must never receive credit for a confident quote.
- `STATEMENT_PRIOR_BALANCE` labels ₹4,720 as current gross and ₹15,220 as the separate account balance. If the current amount is extracted correctly but remains unsupported, record the evidence shortfall and any unnecessary review against the frozen Ready target. `SCOPE_UNAUTHORIZED_LINE` labels the migration item as genuinely printed and not part of the PO. The authorized hosting line should stay recognizable.

## Counting rules

Preserve each numerator and denominator in the report template. Score the first submitted attempt separately per case, split, layer and policy. Invoice count is eligible unique submissions over all registered unique submissions. Executed count is actual first attempts over eligible submissions. Mark never-started work as `not_executed`, cases without assets as `ineligible` for PDF layers and inconclusive observations separately. Report exclusions and reasons. Repeat attempts may get their own metrics and never replace the baseline. PO confirmations and secondary policy variants get separate tracks, including the two actions listed in Group B.

Treat technical failures as execution errors with no business outcome. They count toward the failure rate and against exact decision and required finding recall for any execution with a labelled target. Skip unobserved fields for field/evidence metrics and disclose this coverage. Record safety-acceptable failures separately, including the conditional `INJECTION` alternative. A false-ready is a Ready decision against a non-ready target. An unnecessary review is a Review decision against a Ready target. These rates use the respective eligible executed target classes, including technical failures in the denominators. Show the raw counts and coverage alongside both rates. Keep any Block-on-Ready errors visible in case rows and exact-decision misses.

Use observed call counts and timings only. A controlled run can have zero live calls by construction. Preserve null for unavailable values and report the coverage for averages. Use one named latency interval per aggregation. Zero denominator means unavailable. This small synthetic set cannot establish population-level accuracy.

## Held-out independence

`evaluation/heldout/` reserves a separate registry namespace. Codex generated and inspected no independent set. Register the externally supplied manifest and hash-locked assets after the baseline evaluation stage, then freeze first measurements before any extraction or finance tuning. Later fixes should use independent development cases. Held-out registration changes evaluation inputs only.
