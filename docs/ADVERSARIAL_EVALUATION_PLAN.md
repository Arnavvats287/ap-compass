# Document verification evaluation plan

For architectural review. The code observations are in `ADVERSARIAL_REPRODUCTION_REPORT.md`. Each proposed change requires a later implementation decision.

1. **Document-wide critical-value checks.** Add a bounded reconciliation step in the document adapter before it grants independent evidence. Comparing normalized labelled values across pages should preserve identical repeats and withhold trust for unresolved conflicts. Do not select a higher or lower conflicting value automatically. Primary risk is ambiguous multi-invoice or subtotal scope. Preserve the repeated-summary control.
2. **Material raster uncertainty.** Keep resource caps and distinguish possible payment content from known decoration. Review when the document adapter cannot establish safe absence. A vision claim alone does not verify a bank mismatch. Preserve the decorative raster control. Primary risks are unnecessary review and additional rendering cost.
3. **Fully unreadable rendered documents.** Consider an inexpensive render within the existing parser process and pixel bounds, with a sanitized document error for a fully unreadable result. Keep the visible native control. This narrow protection cannot establish visibility of arbitrary individual PDF objects. Validate cost on large valid pages and respect existing time and memory constraints.
4. **False-positive regression.** Recheck identical continuation summaries, visible text, and benign images before evaluating more complex layouts. The three checked-in benign scenarios establish an offline API baseline.
5. **Offline API evaluation.** Measure document routes, evidence states, final outcomes, sanitized failures, and authority/policy immutability. Keep future acceptance targets distinct from observed behavior. Compare accepted Ready cases as well as required-review and technical-failure cases.
6. **Capped inference evaluation after repairs.** If separately authorized, evaluate a small fixed set and report actual provider usage and uncertainty. Current work made zero Gemini requests.

Existing `MISSING` and `SOURCE_LOCATED_UNVERIFIED` states can represent unresolved critical amounts and trigger existing review findings. Existing sanitized parser error codes can cover a fully unreadable document, subject to confirming their semantics. Payment presence is the likely contract decision: a nullable `bank_instructions` object currently cannot distinguish confirmed absence from possible presence with unreadable details. Prefer an adapter-local conservative gate if the product accepts a technical failure. If the product requires a completed Review assessment while retaining the usable invoice, consider an additive typed integrity signal. Do not construct placeholder bank credentials or weaken existing evidence checks.
